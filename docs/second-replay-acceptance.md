## “最后五分钟”的时间依据

Dodig 的窗口是 `[2026-09-11T20:14:45.787Z, 2026-09-11T20:19:45.787Z)`，终点来自 Gamma 明确的 `finishedTimestamp`。它在采集结束后才发布，所以单独保存了 [结束标签及原始 HTTP 正文](../data/collector/tail5m-validation-20260912/labels-checked/finish-labels.json)。只用该文件补窗口边界，不把事后最终比分、关闭状态或新盘口倒灌进历史。

必须注意两路字段并不完全同刻：Sports 在 `20:19:08.221Z` 已收到 `FT/ended`，其源更新时间是 `20:19:06.992Z`；Gamma 的 `finishedTimestamp` 为 `20:19:45.787Z`。因此这里是**按明确源标签定位的五分钟**，不是外部视频／官方逐分记录已经核准的场上结束毫秒。接收 FT 的时间也不会被擅自当成实际终场时间。

默认所有子盘口跟随全场终点。第一盘、某一局、半场等各自的最后五分钟，需要该阶段自身的可信结束证据；不能拿全场终点或盘口关闭时间代替。`endDate`、预计结束时间和元数据失效时间都不是本功能的实际结束标签。

## 价格及时性与可核查性

记录每一条收到的 WebSocket 消息，然后重建快照＋绝对数量增量，不是每秒轮询一次盘口。逐秒行采用相对终点的半开区间 `[startAtMs,endAtMs)`，只使用右边界之前收到的数据；同一秒内的跌落和反弹分别保留在极值及变化日志中。

本次 Dodig 窗口有 44,064 条带有效源时间的价格增量，源时间到本地接收时间之差为：中位数 89 ms、P95 118 ms、P99 140 ms、最大 388 ms，超过 1 秒的为 0。这是**两个时间戳的差**，不是校准过两端时钟的纯网络延迟，也不能证明服务器未漏发消息。

能看到真实快速变化，例如 `20:16:46.106Z`，Dalla Valle 买一从 0.190 降到 0.083；变化日志保留对应源记录序号 243914。默认 0.1 阈值标记出 10 条快速价格变化，但它们包含互补方向及不同盘口，不是 10 次独立挂单机会，更不是自己的成交证明。

HTTP 快照只作为独立审计：匹配源 hash，或在允许的无 hash 情况下匹配源时间与相同深度，才记为一致。没有可比状态、真实差异、无效 HTTP 响应分别列出。全量深度比对不是只看买一卖一。

窗口开始前的审计计入 `seedSnapshot*`，窗口内计入 `snapshot*`。已发生的差异不会删掉，但新的独立 WS 快照可以恢复之后的盘口。旧响应不能隔离一个已经独立恢复的新快照。同一源 hash 的多条深度消息尚未结束时不抢先判错；未完成校验也不会伪装成通过。

本场窗口内是 119 次一致、0 次差异、0 次不可比；窗口前另有 487 次一致、11 次差异、21 次不可比，全部保留在种子审计中，并非整次运行零异常。最终窗口的六个开放方向同时满足 `observedWindowComplete=true`、`snapshotAuditPassed=true`，但因比分过旧而 `readyForReplay=false`。

## 比分没有与盘口一样完整、及时

本场保存了 9 条比分／阶段变化观测，包括抢七分数、`TB3 → FT` 和 `ended`。这不是 9 个独立得分事件；Gamma 与 Sports 可以重复报告同一状态。

真实反例：Sports 已报 `6-6(4-2)` 后，`20:15:00.636Z` 收到的 Gamma 仍是 `6-6(3-2)`，源更新时间为 `20:13:15.067Z`。后面还出现 Sports 已报 `6-6(6-5)`，Gamma 仍停在 `3-2`。新收到响应不等于里面的比分是新的。

修复后，只有能够通过源时间证明不早于已知 Sports 状态的 Gamma 才能作为回退；否则保留较新的已知比分，超过默认 60 秒就明确标为 `stale`。无时间戳的旧回退也不能悄悄重置状态。因而“盘口 300/300 秒”与“盘口＋新鲜比分整窗就绪”不是同一验收结果。

最终每个方向有 265 秒使用新鲜 Sports、8 秒使用可比的 Gamma 回退，另 27 秒保留已知 Sports 状态但标为过旧。这里的 27 秒是同一比赛的时段，不是六个方向各发生独立缺口；它也不等于已经确认源漏发了 27 秒消息，只表示没有满足默认新鲜度要求。

本场没有提供可用的比赛倒计时；并未验证所有局中的逐分、发球方、赛点或真实落点时刻。状态变化保留 `sourceAtMs` 与 `observedAtMs`，`actualEventTimeKnown=false`。可以研究价格变化与收到比分更新的先后关系，不能据此认定某一秒价格跳动就是某次进球／得分造成的。

## 质量规则与反例

`quality.json` 按方向分别报告：

- `observedWindowComplete`：已观测盘口／已关闭状态是否覆盖整窗；晚发现、缺起始快照、断线、残缺秒、运行外时间不会补成平价。
- `snapshotAuditPassed`：是否具有可比且无未解决差异的窗口审计。它是采样验证，不是交易所逐条签名完整性证明。
- `contextSeconds`：满足配置新鲜度及来源约束的比分／阶段秒数。
- `readyForReplay`：同时满足完整窗口、有效盘口、审计和整窗新鲜上下文的严格筛选，不应只看一个测试通过数量。

本地序号缺口在输出秒之前处理，即使缺口直到窗外才被下一条记录暴露；全局缺口会清除比分基线。某秒中间断流后再收到 PONG，不能把该秒变回完整。比分源时间水位不会被无时间戳消息或可选 slug 的变化绕过。终场标签的 game/slug/嵌套标识冲突也不能串到别场比赛。

旧 90 秒运行 `tennis-research-20260911` 同时作为负例，使用其单独保存的结束标签再导出。三场、102 个方向，没有任何方向通过完整尾窗筛选；原始采集结束甚至略早于 Kolar 那场最后五分钟的起点。其 [质量结果](../data/collector/tennis-research-20260911/tail-final-20260913/quality.json) 不会靠价格延续或未来比分补成完整。

## 重跑和后续回测

复用当前原始数据，不访问网络：

```sh
npm run collect:tail -- \
  --run-dir data/collector/tail5m-validation-20260912 \
  --finish-labels data/collector/tail5m-validation-20260912/labels-checked/finish-labels.json \
  --output-dir data/collector/tail5m-validation-20260912/tail-recheck-new
```

输出目录必须不存在。下一次向前采集可用 README 的有限 30 分钟命令；只有采集真正跨过该场末段且保留可信结束证据，才能得到完整尾窗，启动时间和比赛选择仍会影响覆盖。

现有 `research:backtest` 仍读取历史逐笔成交 dataset，是挂单价／入场窗口的初步筛选；本次 L2 导出没有偷偷接入并冒充已确认的被动成交。后续可用这批数据测不同挂单价的跌破深度、持续时间、价差、直接 SELL 量及回升路径，再明确成交场景假设。挂单价格不固定为 0.70，也不用最后赢家筛选采集对象。

当前先扩充可复核的网球末段样本并处理比分来源局限；乒乓球等球类的状态源和真实阶段终点尚未完成同等级验收。没有声称现有数据足以对所有球类、所有盘口做准确因果回测或确定最优挂单价。
