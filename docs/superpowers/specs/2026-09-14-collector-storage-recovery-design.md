# 体育采集恢复：去重、单场范围与无损存储

用户已确认“完整校验、确保回放兼容后，用可无损还原的压缩文件替换已封存日志”，并要求把去重、恢复采集、数据验收和回测依次完成。本文件记录这一已确认方向的实施约束，延续现有持续采集方案，不重新选择服务器或交易策略。

## 已确认的事实

2026-09-14 全量只读统计：1,212 个原始文件、16,296,115 条记录、78,666,759,290 字节。Gamma 请求响应 29,555,067,496 字节，重复分页记录 29,224,042,464 字节，场次资料 4,316,429,161 字节。实时 CLOB 帧 15,071,581,148 字节。当前服务因 20 GiB 保护余量暂停。已确认同次目录请求的正文重复写入；体育标签还带入长期排名、冠军和优惠券盘口。

## 1. 先控制新增数据

- 在持续模式启用分页正文去重；公共 HTTP 响应原文仍保存一次。分页观察保存该响应的 run、序号、哈希和请求时间引用。不能把一次新 HTTP 观察冒充旧请求，也不能删除失败响应。
- 保持旧有限采集入口的默认记录格式。无法建立可靠引用的自定义发现回调保留完整正文，不能丢弃证据。
- 单场范围排除明确的冠军、排名、赛季统计和其他非比赛事件。接受明确比赛身份或参赛双方／体育玩法证据的单场事件，尤其保留缺少 gameId 的 ITF 和乒乓球比赛。不能按成交量、赔率、赢家或策略收益筛选。
- 盘口帧、成交帧、定时审计快照和每次有效比赛状态观察仍保留。先解决已证实的整页双写，不用丢状态观察来换取空间。

## 2. 原始日志的压缩表示

逻辑分段名仍为 `YYYY-MM-DD-NNNNNN.ndjson`；物理文件可以是这个名称或附加 `.gz`。列举、读取、回放指纹、封口快照和空间统计必须识别两种表示。旧 checkpoint 清单中的逻辑名称不改写，原始解压字节、序号和时钟保持一致。

每个已封口 inode 只压缩一次。所有已知 raw/checkpoint 硬链接别名都发布同一压缩 inode 和完整性说明。删除原未压缩别名前必须完成：来源身份检查 → 独占临时文件压缩 → fsync → 整文件解压哈希与字节数验证 → 发布所有压缩别名和完整性说明 → fsync 目录 → 再检查来源未变。任一步失败保留原始文件。

压缩和原文件并存时读原文件；原文件替换后自动读 gzip，逻辑记录不得重复。中途崩溃留下的并存表示必须可验证、可重试；遇到内容不符、未知硬链接、符号链接或仍在写入的尾段，拒绝替换。CRC/解压错误不能转成“空文件”或通过回放质量检查。

新采集中的封口分段也需要后台压缩。压缩任务与封口导出协调，不能压缩活跃尾段，不能让回放在两遍扫描之间换输入。当前原始接收继续写普通 NDJSON，避免改变实时回调路径。

## 3. 恢复后的验收

先在临时目录验证混合表示、硬链接、失败／重试和旧回放，再对已授权的真实封口数据迁移。保留 20 GiB 保护余量，恢复门槛仍为 21 GiB。实际验收记录新 run、原始记录增长、两种项目的订阅／数据观察、新场次发现和已完成比赛质量；进程存在不能替代行情接收。

## 后续顺序

恢复持续采集后，分别检查每场的终场与阶段终点证据、价格覆盖和比分覆盖；没有实际阶段终点不能伪造盘末／局末窗口。最后把合格逐秒与逐事件数据接入挂单价／入场时机回测，区分价格触达、成交证据与尚缺结算标签的样本，报告样本不足而不制造收益结论。其他球类在基础链路稳定后按已核验的体育标签扩展。
